# Spec: S2b2 编排助手拆单链（聊出来 → 确认 → 建单）

- **topic**：atd-s2b2-orchestration
- **状态**：v1 草案（SPEC_DRAFT，待澄清 3 项）
- **日期**：2026-09-26
- **上游**：Epic §4.3/§9（S2b2 行）；S2b1（聊天容器）/S3（排队与自动流转）已交付
- **产品定位承接**（用户原话锚定）：复刻「与人对齐需求」的协作形态——讨论需求 → 产出**只有业务语言的 spec** → 人确认 → 创建工单 → 之后交给流程处理。S2b1 交付了「讨论」，本 Story 交付「产出与落单」。

## 背景

现在聊天里能讨论需求，但讨论成果要靠人手工去工作台建单。本 Story 打通最后一公里：**编排助手**在会话里调研代码、产出业务语言 spec 与任务拆解草稿，你编辑确认后一键落单——STORY+任务链带依赖与执行者自动建好，后续执行交给已交付的编排链自动流转（无需逐张人工放行）。

## 范围

**做**（用户得到什么）：

1. **编排助手**：新会话可选「编排」助手（与普通讨论助手同款视野与行为三档）；它的特长是——听懂需求后主动看仓（调研），然后给出：**业务语言的 spec 草稿 + 任务拆解计划**（每张任务卡含：标题/业务 spec/目标仓/执行 worker/依赖关系/涉及文件）
2. **计划卡**：聊天流中自动把助手的拆解计划渲染成**可编辑的计划卡**（改标题、改描述、调依赖、补文件清单都在卡上完成）；格式未识别时原样显示文本，不崩
3. **确认门**：卡上「确认建单」→ 一次性建立 STORY + 全部任务 + 依赖链 + worker 预绑定 + spec/文件集冻结 → 跳转 STORY 详情页看泳道
4. **会话内切换助手**：普通讨论 ↔ 编排，历史延续不换会话
5. **自动流转**：建好的任务链交给既有编排链自动执行（含 S3 排队/闸门/重试语义，零新做）

**不做**：不经确认的自动建单；spec 变更单/版本管理（既有域概念另走）；跨 workspace 的计划链（既有约束）；质量门工单化（Epic 非目标）；计划草稿落库（草稿活在会话文本里，确认的是编辑后的最终态）。

## 验收标准（初版，用户可验证）

1. **产出**：会话中讨论一个真实需求 → 编排助手调研仓后给出 spec+任务计划卡（业务语言，含目标仓/依赖/文件集）
2. **编辑**：卡上改任务标题/调依赖/补文件清单后确认 → 建出的单与编辑后内容一致
3. **落单**：确认后 STORY+任务全部建立、依赖成链、worker 预绑定、spec 快照冻结；**建单要么全成要么全不成**（中途失败不留半链）
4. **自动流转**：链上首任务自动放行执行，前序 DONE 后继自动接力（选一张任务真跑通 DONE）
5. **泳道**：STORY 详情页泳道呈现链状态（既有能力回归）
6. **无干扰**：普通讨论会话行为不变；编排助手视野/三档行为与普通助手一致；fence 全绿
7. **自验证**：交付后跑无头浏览器+视觉解析复核（S2b1 验收反馈同款流程）+ 真机冒烟

## 待澄清

1. **助手形态**：独立「编排」助手（建会话时选，可中途切换）vs 单助手身兼讨论+拆单（推荐**独立助手+可切换**——职责清晰的系统提示词，产出合同遵循度更高）
2. **确认门 UI**：计划卡在聊天流内联编辑（推荐）vs 弹窗编辑后提交
3. **多轮计划**：同一会话多次拆单（每次确认各自成链）——按此理解对吗？（推荐是：聊天天然多轮，每张确认卡独立落单）
