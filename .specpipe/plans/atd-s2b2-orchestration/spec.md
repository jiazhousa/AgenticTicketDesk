# Spec: S2b2 编排助手拆单链（聊出来 → 确认 → 建单）

- **topic**：atd-s2b2-orchestration
- **状态**：v2（三项澄清落定，待审查）
- **日期**：2026-09-26（v1 草案 / v2 澄清收敛）
- **上游**：Epic §4.3/§9（S2b2 行）；S2b1（聊天容器）/S3（排队与自动流转）已交付
- **澄清记录**（2026-09-26 用户拍板）：① **单助手双职责**——讨论与拆单同一助手（产出合同并入其系统提示，无独立编排助手、无切换）② 确认门=聊天内计划卡编辑 ③ 同一会话多次拆单各自成链互不影响
- **对 Epic 的偏离清单**：① Epic §9 原文「oracle/explorer agent 定义 + profile {{agent}} 变量」收敛为**单助手双职责**（用户拍板）——独立编排 agent 与会话内切换不做，产出合同以系统提示承载；② 「人工确认门」形态=聊天内计划卡（非独立页面）
- **产品定位承接**（用户原话锚定）：讨论需求 → 产出**只有业务语言的 spec** → 人确认 → 创建工单 → 之后交给流程处理。S2b1 交付了「讨论」，本 Story 交付「产出与落单」。

## 背景

现在聊天里能讨论需求，但讨论成果要靠人手工去工作台建单。本 Story 打通最后一公里：助手在会话里调研代码、产出业务语言 spec 与任务拆解草稿，你在聊天内的计划卡上编辑确认后一键落单——STORY+任务链带依赖与执行者自动建好，后续执行交给已交付的编排链自动流转（无需逐张人工放行）。

## 范围

**做**（用户得到什么）：

1. **双职责助手**：现有聊天助手新增拆单职责——你明确提出要提单/拆单时，它先调研仓，再产出**业务语言 spec 草稿 + 任务拆解计划**（每张任务卡含：标题/业务 spec/目标仓/执行 worker/依赖关系/涉及文件预填）；日常讨论行为不变
2. **计划卡**：聊天流中自动把助手的拆解计划渲染成**可编辑的计划卡**——改标题/描述、增删任务、调依赖、补文件清单、换目标仓/worker 都在卡上完成；格式未识别时原样显示文本，会话不受影响
3. **确认门**：卡上「确认建单」→ 一次性建立 STORY + 全部任务 + 依赖链 + worker 预绑定 + spec/文件集冻结 → 跳转 STORY 详情页（泳道看链）
4. **自动流转**：建好的任务链交给既有编排链自动执行（S3 排队/闸门/重试语义照旧，零新做）；**多次拆单各自成链互不影响**

**不做**：不经确认的自动建单；spec 变更单/版本管理（既有域概念另走）；跨 workspace 的计划链（既有约束）；质量门工单化（Epic 非目标）；计划草稿落库（草稿活在会话文本里，确认的是编辑后最终态）；独立编排助手与会话内切换（澄清①）。

## 验收标准（终版）

1. **产出**：会话中讨论一个真实需求 → 明确要求拆单 → 助手调研仓后给出 spec+任务计划卡（业务语言，任务含目标仓/依赖/文件集预填）
2. **编辑**：卡上增删任务/调依赖/换目标仓/改文件集后确认 → 建出的单与编辑后内容一致
3. **落单**：确认后 STORY+任务全部建立、依赖成链、worker 预绑定、spec 快照冻结；**全成或全不建**（中途失败不留半链）
4. **自动流转**：首任务自动放行执行，前序 DONE 后继自动接力（选一张任务真跑通 DONE，S3 排队/闸门照旧生效）
5. **泳道**：确认后跳 STORY 详情，泳道呈现链状态（既有能力回归）
6. **多轮**：同一会话再次拆单 → 新计划卡独立确认独立成链
7. **无干扰**：纯讨论会话行为不变；助手视野/三档行为与 S2b1 完全一致；fence 全绿
8. **自验证**：交付后跑无头浏览器+视觉解析复核 + 真机冒烟（S2b1 验收反馈同款流程）

## 业务规则

1. **计划块协议**：助手按约定格式输出完整计划块（STORY 概要+任务清单）；聊天界面识别该块渲染为计划卡；未识别不崩（原样文本），不阻塞会话
2. **确认门是唯一建单入口**：草稿不建单；确认提交的=计划卡编辑后的最终态
3. **原子建单**：STORY+任务+依赖+绑定一次事务完成——任一环失败全部不建并明确报错
4. **校验沿用既有规则**：目标仓 ∈ workspace 声明（主/readable）、worker ∈ 注册表、依赖限同计划内任务、环检测——违规项在卡上标红并阻止确认（提交前预校验）
5. **冻结语义沿用**：任务 spec（业务语言）/plannedFiles 随建单冻结（S3 文件集校验参与）；STORY 描述=spec 草稿概要
6. **流转语义沿用**：建单后任务处于可自动放行态（有 parent+预绑定），链式流转/排队/闸门/重试全部走既有机制
7. **助手行为不变**：双职责仅扩系统提示（产出合同），视野五规则与三档行为零变化
8. **确认后会话继续可用**：追问、再拆单、继续讨论均可
9. **计划卡范围上限**：任务数/文本长度 MVP 不设硬上限（体验问题按需优化）

## 关键风险

| 风险 | 应对 |
|---|---|
| 助手产出格式遵循度（单助手双职责的提示词工程） | 产出合同写进系统提示（格式范例+字段说明+业务语言要求）；识别失败降级文本不阻塞；真机验收按「产出→渲染→确认→建单」全链把关 |
| 计划卡解析与 markdown 渲染的耦合 | 计划块识别在渲染层之前（独立解析步骤），与 markdown 渲染互不干扰 |
| 原子建单的回滚完整性 | 服务端单事务（建 STORY→任务→依赖→绑定），失败整体回滚+错误明细返回卡上 |
| 用户编辑后的计划合法性 | 提交前服务端预校验（规则 4），违规项卡上标红阻止确认 |
